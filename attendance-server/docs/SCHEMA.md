## The three that carry the design

### `punch_events` — append-only
Never updated, never deleted. No `updated_at` column, deliberately. A mistaken
punch is fixed by adding a `corrections` row on top; both stay visible.

`uq_punch_idempotency` on `idempotency_key` is what makes the offline kiosk
queue safe. The database rejects the duplicate — not application code, which
two concurrent requests can both slip past.

### `attendance_days` — derived, not a source
A cache of what the rollup computes from punches. Nothing here cannot be
rebuilt. A rule change means recompute, not migrate.

Composite primary key `(employee_id, date)`: exactly one row per person per day,
enforced by the database rather than by remembering to check.

`flags` is a native `text[]`. Flags are only ever read together with their day
and never queried across days on their own, so a join table would add a join to
every read for nothing.

### `leaves` — why it is in migration 001
Without it, somebody on approved leave and somebody who did not turn up are
indistinguishable: zero punches, both ABSENT. Every absence figure would be
wrong from the first month.

Adding it later is not a new table — it is a rollup rewrite plus a backfill of
every historical day.

## Conventions

| Decision | Reason |
|----------|--------|
| UUID primary keys | The kiosk generates ids offline; integers leak headcount and invite enumeration |
| `server_default=func.now()` | The database clock, not the app server's — two instances with drifting clocks otherwise write inconsistent ordering |
| Status columns, never DELETE | Deleting an employee orphans their punches and tasks |
| `Numeric` for `min_hours` | 8.5 must be exactly 8.5; binary floats turn into payroll arguments |
| `JSONB` in `audit_log` | Indexable, so "every change to this person's role" stays answerable |
| `ivfflat` index on embeddings | Without it every face match is a sequential scan, with somebody standing at the kiosk |

## Two traps already fixed in this migration

**pgvector import.** Autogenerate writes `pgvector.sqlalchemy.vector.VECTOR(...)`
but adds no import, so a generated migration dies with `NameError` on first run.
`alembic/script.py.mako` now imports it, so every future migration is correct
without anyone remembering.

**Orphaned ENUM types.** `sa.Enum` creates a Postgres TYPE alongside the table,
and `drop_table` does not drop it. Without the explicit `DROP TYPE` statements,
`downgrade` appears to succeed, leaves eight orphaned types behind, and the next
`upgrade` fails with *"type employee_status already exists"* on a database that
looks empty.

This only shows up the second time you run the migrations, which is why it
reaches production so often. The cycle `upgrade → downgrade → upgrade` has been
run against a real Postgres and passes.

## Commands

```powershell
alembic upgrade head          # apply
alembic downgrade -1          # back one
alembic downgrade base        # back to empty
alembic current               # where am I
alembic history --verbose     # what exists
alembic revision --autogenerate -m "add x"
```

Always read an autogenerated migration before running it. Autogenerate is a
first draft, not an answer — it cannot see a rename, so it writes a DROP and a
CREATE, and that is data loss.
